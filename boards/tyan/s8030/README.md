# Tyan S8030

AMD SP3, one socket, EPYC 7002 (Rome) or 7003 (Milan). Status: boots
Linux with an EPYC 7502P (Rome) on the S8030GM2NE test bench.

One board id, `tyan-s8030`, and one build for both generations: the
platform's `rome` and `milan` features are enabled on its dependency, and
the reset image picks the generation from the CPU at runtime. fstart packs
each generation's PSP partition into its own 16 MiB half; its `0x62`
entries name a copy of the one reset image, and the FFS exists once, in
the lower half.

```sh
cargo fbuild build --board tyan-s8030 --release
cargo fbuild assemble --board tyan-s8030 --release \
    --donor /path/to/8030V404.ROM                          # -> tyan-s8030.rom
```

## Settings

With the UEFI payload, CrabEFI's firmware settings menu (`F` in the boot
menu) offers the vendor Setup knobs fstart implements: Restore on AC power
loss, the bifurcation of each x16 slot (the vendor's `Setup[0x194..0x198]`),
PCIe compliance mode, the two i210 links and the onboard VGA link. They are
stored in the settings store in flash and apply at the next boot; a new
image starts with an empty store. A bifurcation set that does not give a
valid DXIO lane map is ignored with a warning in the boot log.

The board default is the vendor's (every slot x16); the
`tyan-s8030-pcie3-x4x4x4x4` variant defaults PCIE#3 to x4x4x4x4 for an NVMe
carrier (the test bench), so it boots right before anything is stored.

```sh
cargo fbuild assemble --board tyan-s8030-pcie3-x4x4x4x4 --release --payload uefi --donor ...
```

## Donor image

The AMD firmware (PSP, ABL, SMU, PMU and DXIO firmware, APCB) is vendor
firmware and not part of this repository. `--donor` takes it from a vendor
image: fbuild extracts the files the platform's Rome and Milan tables name
(`fbuild blobs` does the same into a directory for `--blobs`), and fstart
packs them into its own layout; nothing else of the donor is kept. The Tyan
v4.04 dual image (`8030V404.ROM`, 32 MiB, SHA-256 pinned in the sp3
workspace's `firmware/donors/SHA256SUMS`) gives both generations; a board's
own flash backup gives what it carries (the test bench's: Rome only, so the
image is the Rome half).

| | Both generations | Rome-only donor |
|---|---|---|
| Lower half | Rome partition from `0x20000` | Rome partition from `0x20000` |
| Upper half | Milan partition from `0x20000` | none: a 16 MiB image |
| Reset image (`0x220000` bytes, linked at `0x75de0000`) | `0xde0000` in each half | `0xde0000` |
| FFS | `[0x600000, 0xda0000)`, lower half only | same |
| Settings store | `[0xda0000, 0xde0000)`, erased | same |

A Rome boot reads the FFS through ROM2; a Milan boot, from the upper half,
through the FCH ROM3 window above 4 GiB.

## SKUs: S8030GM2NE and S8030GM4NE-2T

The two SKUs run the same vendor image and this crate does not tell them
apart:

- GM4NE-2T adds an Intel X550-BT2 (2 × 10GBASE-T) on lanes 76–79. The
  lane map always describes that x4 port; on GM2NE nothing is attached and
  the link does not train.
- No strap, GPIO, EEPROM or IPMI value in the vendor firmware selects a SKU,
  and the SMBIOS data says S8030GM2NE on both (BOARD_S8030 §3).

Both have the AST2500 BMC, two i210 ports, five PCIe x16 slots, two
SlimSAS x8 (four NVMe x4), fourteen SATA ports (two connectors, three
SFF-8643) and two M.2 sockets (PCIe x4 or SATA, detected per socket).

## Layout

| File | Content |
|---|---|
| `src/dxio.rs` | lane map and OEM patches (bifurcation, speed, compliance, LAN, VGA, M.2, BMC Gen3 cap) |
| `src/gpio.rs`, `src/gpio/table.rs` | `$A10` pad table (generated), M.2 detect pads, Rome GPIO4/5 |
| `src/policy.rs` | DF, SMU, NBIO, CCX, DXIO policy and FCH power-failure / spread-spectrum values |
| `src/bmc.rs` | AST2500 LPC decodes, Super I/O, SCU, COM1 console, IPMI KCS, Tyan OEM M.2 query, ACPI inputs |

`src/gpio/table.rs` and `src/dxio/tuning.rs` are generated by
`.venv/bin/python -m tools.gen_board_s8030` in the sp3 analysis workspace.
