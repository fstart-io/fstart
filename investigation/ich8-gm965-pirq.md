## Key Code

### Coreboot `_PRT` placement

Coreboot static DSDT puts both chipset ASL blocks inside the PCI root bridge:

```asl
Scope (\_SB) {
	Device (PCI0)
	{
		#include <northbridge/intel/gm965/acpi/gm965.asl>
		#include <southbridge/intel/i82801hx/acpi/ich8.asl>
	}
}
```

Additionally, `southbridge_fill_ssdt()` calls `intel_acpi_gen_def_acpi_pirq(device)`, which writes a separate SSDT scope for the root bridge:

```c
intel_write_pci_PRT("\\_SB.PCI0", pin_irq_map, map_count, &pirq_map);
```

So expected placement is:

- `\_SB.PCI0._PRT` - generated dynamically from root-bus devices and RCBA DxxIR.
- `\_SB.PCI0.PEGP._PRT` - GM965 PEG bridge downstream routing.
- `\_SB.PCI0.RP01..RP06._PRT` - ICH8 PCIe root-port downstream routing via `IRQM(RPPN)`.
- `\_SB.PCI0.PCIB._PRT` - X61-specific secondary PCI bridge/dock routing from `acpi/ich8_pci_irqs.asl`.
- PIRQ link devices live at `\_SB.PCI0.LPCB.LNKA` ... `LNKH`.

### Coreboot PCIe/PEGP downstream `_PRT` entries

`PEGP._PRT`: APIC pins 0..3 -> GSIs 16..19; PIC pins 0..3 -> `LNKA`, `LNKB`, `LNKC`, `LNKD`.

### Coreboot generated `\_SB.PCI0._PRT`

Generated by `rcba_pirq.c`: for each enabled root-bus device with `PCI_INTERRUPT_PIN` A-D, map:

- non-PCH slots (<19, >31, or 24): PIRQ is 1:1 from PCI pin.
- PCH slots 19..31 except 24: read DxxIR nibble for the advertised PCI pin.
- APIC GSI = `16 + pirq_idx(pirq)`.
- PIC source path = `\_SB.PCI0.LPCB.LNK[A-H]`.

For X61 ICH8 functions, after the coreboot X61 late RCBA values below, the expected root-bus rows are:

```text
00:19 pin A -> PIRQB -> GSI 17 -> LNKB   (GbE, if enabled)
00:1a pin A -> PIRQE -> GSI 20 -> LNKE   (UHCI4)
00:1a pin B -> PIRQF -> GSI 21 -> LNKF   (UHCI5)
00:1a pin C -> PIRQG -> GSI 22 -> LNKG   (EHCI2)
00:1b pin B -> PIRQB -> GSI 17 -> LNKB   (HDA)
00:1c pin A -> PIRQE -> GSI 20 -> LNKE   (RP01)
00:1c pin B -> PIRQF -> GSI 21 -> LNKF   (RP02)
00:1d pin A -> PIRQA -> GSI 16 -> LNKA   (UHCI1)
00:1d pin B -> PIRQB -> GSI 17 -> LNKB   (UHCI2)
00:1d pin C -> PIRQC -> GSI 18 -> LNKC   (UHCI3)
00:1d pin D -> PIRQD -> GSI 19 -> LNKD   (EHCI1)
00:1e pin A -> PIRQG -> GSI 22 -> LNKG   (PCI bridge)
00:1f pin A -> PIRQH -> GSI 23 -> LNKH   (SMBus, D31.F3)
```

## Architecture

Fstart already has topology data that can avoid embedding `PCI0` in reusable drivers:

- `board.ron`: `southbridge` has `acpi_parent: "northbridge"`; northbridge has `acpi_name: "PCI0"`.
- Codegen computes ACPI paths by walking `acpi_parent`/physical parent (`model.rs` lines 247-287).
- `caps_tables.rs` wraps a child driver’s AML with `scoped_aml_with_root_fragments(parent_path, ...)` when a parent path exists.
- `fstart-acpi` automatically wraps normal device AML inside `\_SB_`, while `Scope("\\")` root fragments are split out and kept at DSDT root.

Therefore the ICH8 driver should emit AML relative to its ACPI parent (the PCI root bridge), not absolute `\_SB.PCI0` content. Board/mainboard code should get or be generated with the same topology-derived path instead of spelling `PCI0`.

## fstart discrepancies

1. **Missing `\_SB.PCI0._PRT`:** fstart ICH8 ACPI emits `_PRT` only under RPxx and PCIB. Coreboot also emits root-bridge `_PRT` dynamically via `rcba_pirq.c`.
2. **APIC-only `_PRT` packages:** fstart PEGP, RPxx, and PCIB `_PRT` are `Name("_PRT", Package(...GSI...))`. Coreboot uses `Method(_PRT)` with `If (PICM)` and PIC-mode link-device sources.
3. **PCIB APIC rows match but PIC rows missing:** fstart `PCIB` rows match X61 APIC entries, but lacks the PIC branch using `LNK[A-G]`.
4. **Root-port routing not topology/runtime accurate:** fstart hardcodes packages by RP device name. Coreboot routes by hardware `RPPN` using `IRQM(RPPN)` so remapped/root-port-numbered devices stay correct.
5. **X61 RCBA D26 missing in fstart board:** `boards/lenovo-x61/board.ron` late RCBA omits `d26ip: 0x30000021` and `d26ir: 0x0654`. Fstart leaves defaults `D26IP=0x10000021`, `D26IR=0x0003`, which misroutes UHCI4/UHCI5/EHCI2 versus coreboot.
6. **Hardcoded absolute `PCI0` paths:** fstart ICH8 comments/config and X61 mainboard AML hardcode `\_SB_.PCI0...`; this is fragile when the root bridge ACPI name is supplied by topology.
7. **Hardcoded RCBA address in ACPI:** fstart GM965 and ICH8 ACPI use `0xFED1C000` directly instead of `config.rcba`; X61 uses that value, but reusable ICH8 should not.
8. **Missing/partial root-bus device nodes:** fstart ICH8 ACPI omits LAN and IDE nodes while X61/coreboot has 00:19.0 and 00:1f.1 enabled. Even if minimal nodes are acceptable, root `_PRT` still must cover their interrupts when enabled.

## Topology-driven fix plan

1. Add a reusable fstart ACPI helper for PCI `_PRT` methods: APIC GSI package when `PICM`, PIC link-source package otherwise.
2. Teach ICH8 ACPI generation to emit relative AML for its parent PCI root scope. Do not write `Scope("\\_SB.PCI0")` in the driver; let codegen wrap using `acpi_parent`.
3. Generate the root bridge `_PRT` from an explicit ICH8 root-bus interrupt map derived from chipset config/topology: enabled functions + DxxIP/DxxIR/late_rcba. Emit it as relative `_PRT` in the southbridge contribution so codegen places it under the actual root bridge path.
4. Generate PIRQ link source paths from the topology-derived LPCB path, or use relative paths (`LPCB.LNKA` from within PCI root, `^LPCB.LNKA` from child bridges) to avoid spelling `\_SB.PCI0`.
5. Replace RPxx static `_PRT` packages with coreboot-style `IRQM(RPPN)` or equivalent per-port generated method including both APIC and PIC branches.
6. Keep `PCIB._PRT` board-specific, but represent the X61 dock/Ricoh rows as data in board config or a mainboard ACPI contribution that is scoped under the topology-discovered `PCIB`, not hardcoded `PCI0`.
7. Fix `boards/lenovo-x61/board.ron` late RCBA to include `d26ip: 0x30000021` and `d26ir: 0x0654`.
8. Replace `crates/fstart-mainboard-lenovo-x61/src/lib.rs` absolute `\_SB_.PCI0.LPCB...` references with generated/parameterized paths from the board topology. The current code has no parameter path in `AcpiDevice::dsdt_aml`, so likely add an ACPI context/path plumbing layer rather than adding more string constants to drivers.

## Open questions / risks

- Coreboot's dynamic `\_SB.PCI0._PRT` is hardware-observed: it emits rows only for devices whose `PCI_INTERRUPT_PIN` is A-D at runtime. The ICH8 rows above are exact for the configured X61 ICH8 functions and RCBA map; non-PCH GM965 devices such as IGD are added only if their PCI config advertises an interrupt pin.
- The current `AcpiDevice::dsdt_aml(&self, config)` API does not pass the computed ACPI path/context, so a clean no-hardcoded-PCI0 fix probably needs an API/codegen extension.
